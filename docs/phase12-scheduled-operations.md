# Scheduled Phase 12 operations

Use `venv\Scripts\python.exe scripts\run_phase12_operations.py run` from the repository root. This dedicated action processes SA, FL1, PD and BL1 independently using the unchanged Phase 12 admission, settlement, feature/RNG, replay and scientific contracts. It never calls the nightly training pipeline or any activation API.

The default retry key is the current UTC hour. Repeating that key references the same immutable report. `--key NAME` gives an explicit manual retry identity; reuse it after interruption. An unfinished invocation is resumed before another invocation starts. A new hourly invocation can collect the next earliest qualifying fixture even when the schedule is unchanged. No fixture is backfilled after its cutoff. A published pair is its own atomic seal; recovery detects publication after the invocation's starting journal head and never spends a second admission in that invocation. Completed league outcomes are resumed without repeating work. The runner and existing league locks are OS locks released on process death; contention is retriable and does not establish a protocol violation. Do not delete lock files.

Transport failures and HTTP 408/429/500/502/503/504 receive at most three attempts, separated by 2 and 5 seconds. Each source response and failed attempt is archived independently. Qualification retries only when archived transport failures explain the rejection; identity, overlap or score disagreement is never repaired by retrying. Old successful retrievals are not substituted for failed current retrievals. Fixed cutoffs are rechecked by the original collector after acquisition and inference, including on delayed retries.

Every invocation produces or references `baselines/phase12/phase12-prospective-20260908-v1/operational/report-NNNNNN/report.json`. Intent, per-league claim and outcome files support crash recovery; `report.json` is published last. It binds numbered report history, source archives, complete ordered cohort indexes, checkpoints, interim metrics/reliability, incidents, before/after counts and protected hashes. A report with an unverifiable league records failure and cannot receive a successful offline verification. Later invocations can retry that league, but historical failed verification is never relabeled as success. Source-blocked leagues with replayable existing evidence receive explicit degraded reports. No sealed file is replaced.

Scientific state is the unchanged Phase 12 state. `authorization.state` separately exposes `BLOCKED_MISSING_PROSPECTIVE_CONTRACT` for the current Phase 9 deployment specs, including when a future scientific state becomes `DECISION_READY`. A binding, if externally supplied in a separately authorized phase, still requires separate Phase 8 review. This runner never authorizes activation. Calendar horizons, bootstrap size and decision rules have no CLI overrides.

Run `venv\Scripts\python.exe scripts\run_phase12_operations.py verify` for independent network-free replay of every pair/settlement and recomputation of every checkpoint, with report-chain, source-hash and protected-file validation. Immutable receipts appear under `operational/verifications/`. The verifier exits unsuccessfully on missing/reordered/changed evidence. Report JSON remains immutable; the receipt references its exact hash.

Before sealing the first operational package, run focused, protected and full suites using `tmp/phase10_guarded_pytest.py`, then use `certify-tests --focused PATH --protected PATH --full PATH` to bind the XML evidence. It compares against the sealed Phase 12 full-suite reference; the six inherited failures remain separate. It does not permit a new failure.

## Windows scheduling

This repository already supports Windows Task Scheduler (`BettingPartnerNightly`). After verification, run `powershell -NoProfile -File scripts\register_phase12_task.ps1`. The dedicated task starts hourly, ignores overlapping launches, runs missed starts when available, and uses the repository Python runtime without a visible window. It runs under the current user's interactive session without saving a password. The user must be logged in and the machine awake/available; offline periods create no retrospective predictions. The next available run handles legitimate completed results and records missed admission cutoffs. A six-hour execution limit leaves a recoverable intent if a provider or runtime stalls.

Inspect the task's LastTaskResult and the latest numbered report. Exit 0 means a completed or duplicate non-degraded report, 2 means a completed degraded report, and an exception means unfinished work or integrity failure. Investigate scientific violations before any further admission; no automatic scientific repair exists. Disable this dedicated task to pause operations. No existing nightly job is modified.
